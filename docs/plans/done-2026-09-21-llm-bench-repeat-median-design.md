# 压测重复取中位数（题升 v6）

> 落盘日期：2026-09-21
> 状态：已完成

## 为什么

调研了一圈现成工具（vLLM 官方 GuideLLM、阿里 EvalScope perf、NVIDIA AIPerf、vllm bench serve 的 BFCL 工具轴）。结论是我们这把尺子的定位站得住——它打的是旗鱼自己那条请求路径（同一套系统说明 + 用户话 + 25 个工具、同一个流式通道），并且三轴合一给一个可横比的分，装在软件里点一下就跑；开源里没有同时满足这三条的。

但对照之下暴露出一个真短板：**成熟工具都做预热 + 重复多次 + 报分位数，我们每档只打一发。** 2026-09-21 真机两轮里，火山 dsV4.1flash 的 4000 字档首字延迟一次 2.2 秒、一次 5.1 秒——单发数据噪声大到足以让跨机器比较误判。

冷启动的设计不用改（各档之间不吃缓存是刻意的），重复几次取中位即可。

## 定下的取舍（2026-09-21 与用户确认）

1. **取中位那一发的整行**，不是每个指标各取中位数。拼出来的组合不是真实发生过的一次，容易自相矛盾（首字来自第 1 发、写速来自第 3 发）。排序键用首字延迟。
2. **任一发失败，这一档就算没过**，备注写明第几发挂的。接口不稳定本来就是要暴露的东西，也跟现在单发的判法一致。
3. **发数用户自己选**（1 / 3 / 5），默认 3。标准尺子该一视同仁，赶时间时自己调成 1。报告里写明这次是几发，两份报告对着看时能确认口径一致。
4. **各发之间同样不许吃缓存**。这条是这次改动的命门：第 2、3 发若命中上一发的提示缓存，中位数量到的是「暖」数据，比现在单发还不准。

## 怎么改

### 执行顺序：外层循环整套跑 N 遍

不是「同一档连打 3 发」，而是「整套（各长度档 + 工具 + 并发）跑完一遍，再跑第二遍」。两个好处：三发落在不同时间段，分散网络与服务端排队的相关噪声；第一遍跑完表就填满了，用户先看到完整结果，后面两遍逐步精化。

### `suite.ts`

- `benchIsolateLine(targetChars, axis, lane, shot)` 多一个「发=k」。隔离串进 system 和 user 开场白，垫料会自动补偿字数，各发的目标字数仍严格相等。
- `BENCH_SUITE_VERSION` → `sailfish-bench-v6`（测法变了，v5 报告不可比）。

### `types.ts`

- `BENCH_DEFAULT_SHOTS = 3`、`BENCH_SHOT_CHOICES = [1, 3, 5] as const`。
- `BenchReport.shotsPerRung: number`——口径进报告。
- `BenchRungResult.shots?: BenchRungResult[]`——每一发的原始数据。展示的那一行是它的投影（中位那一发），不是另一份真相。
- `StartBenchInput.shots?: number`。

### `runner.ts`

- 外层 `for (shot of 0..N-1)`，内层照旧跑各档 / 工具 / 并发；每次结果 push 进对应 rung 的 `shots`。
- 每跑完一发就重算展示行：全过 → 按首字延迟排序取中间那一发；有失败 → 取第一个失败的那一发当展示行（错误、备注跟着它走），`success=false`。
- 并发：每一路各自按自己的多发取中位；任一遍里那一路挂了，那一路就算没过。
- 工具轴：一发里 call + after 成对跑，代表发按 call 的首字延迟取中位，保证展示的两步来自同一发。
- 进度事件带「第几发」，中途停止时已有的发照常保留。

### `score.ts`

不动。它拿到的仍是每档一组代表数。

### `llm-bench.html`

- 工具条加「每档打几发」下拉（1 / 3 / 5，默认 3）。
- 状态区显示「第 2/3 遍」。
- 长度档表加一列「首字波动」，写最快~最慢（只有一发时显示「—」）。
- 分数卡元信息加「每档 3 发取中」。

### 测试

- 各发隔离串互不相同（题面）。
- 三发首字 100/300/200 → 展示行取 200 那一发的整行数据。
- 第 2 发限流 → 该档没过，备注含「第 2 发」。
- `shots=1` 时行为与今天完全一致。

## 不做

- 不报 p95/p99：三五发算分位数没有统计意义，报了反而像模像样地骗人。
- 不做预热请求：预热会污染「每档都冷启动」这条设计。
- 不按成功率打折扣分：与「任一发失败即没过」的判法冲突。
- 不做变速率 / 泊松到达 / 高 QPS 压力测试——那是 GuideLLM 的活，我们不跟它比这个。

## 真机复验（2026-09-21，火山 dsV4.1flash，4000 / 32000 两档 × 3 发）

| 项 | 三发首字 | 展示的那一发 |
|---|---|---|
| 4000 字 | 4510 / 6517 / 6118ms | 第 3 发（6118ms）✓ 中位 |
| 32000 字 | 7124 / 5797 / 5212ms | 第 2 发（5797ms）✓ 中位 |
| 工具 | 2336 / 7238 / 2549ms | 发起调用与处理结果都取第 3 发 ✓ 同发 |
| 并发三路 | 各自三发 | 各自取各自的中位 ✓ |

同一条线路上单发能差出 40%（4510 → 6517ms），正是这次要治的。

## 审查后追加

Claude 审查抓到两处真 bug，都补了会失败的回归测试（先回退修复确认测试变红，再改回）：

1. **展示行会混发**：`showShot` 用 `Object.assign` 覆盖，这一发没有的字段会留着上一发的值。断流那一发没量到首字，行里却挂着上一发的 `ttftMs` / `actualPromptTokens`——恰恰是「拼出一行谁也没跑过的数」。改成覆盖前先抹掉这一发没有的键。
2. **中途停止会作废已打完的发**：`markAborted` 把 `running` 的行改成 `aborted`，连带把第一遍跑出来的中位行抹了（并发三路整项归零）。改成：行里已有发就回填代表行，只有真没数据的才标 aborted。

另外：偶数发（只有中途停止才凑得出）改取偏慢那一发，宁可报保守；`shotsPerRung` 收尾时按实际打成的发数写，中途停止不再顶着「每档 3 发」；SPEC 补一句「发数越多撞上偶发限流的机会也越大」这条认了的取舍。
