# 模型接口压测 SPEC

> Last verified: 2026-09-21

## 职责

给自己一把固定的尺子：单独一个压测控制台，按旗鱼真实打法扫一遍当前这套模型接口——上下文变长、写得慢不慢、真的在调工具、同时打几路。换机器、换模型都用同一套题，报告能直接拿来比较。

## 设计目标

### 单独一把尺子，不塞进调试，也不进秘书主界面

- **问题**：压测是主动打、出对照表；调试是旁观刚才发生了什么。挤在一起，两边都脏。压测也不是秘书能力，不能进任务、联络或设置。
- **成功标准**：
  1. 有自己的压测控制台，和调试控制台并列，像网站旁边另有一把压测尺子，各干各的。
  2. 设置、任务、联络、关切这些正经功能看不见、也用不到它。
  3. 调试控制台继续只记流水；压测跑的时候可以同时开着调试去盯单次请求，但那是旁观，不是同一块屏。
- **关键取舍**：复用旗鱼已经配好的模型和密钥，但压测是旁边的独立工具，不是旗鱼面向日常使用的功能。
- **明确不做**：不做进调试窗口、不做设置页、不装到对方那台算力机器上。换机器等于换模型配置里的接口地址，再跑同一套题。

### 题冻住，才能比较

- **问题**：每次用当时旗鱼正在用的系统说明去打，题已经变了，两份报告比的不是机器和模型。各家怎么数 token 也不一样，按 token 分档对不齐。
- **成功标准**：
  1. 题是一份带版本号的固定中文题。每一档都带齐三块：系统说明、用户话、完整工具清单，份量和形状像旗鱼真在发，不是缩成三句话、三个工具。
  2. 不读本机记忆、历史对话、当时的系统说明或当时的工具清单。旗鱼以后改了提示词，旧报告仍能和新跑的比。
  3. 分档按字数，不按各家 token。同一档发出去的是同一套字。
  4. 接口回报的 token 仍记在报告里，那是这款模型自己的算法，不拿来定档。
  5. 报告写清题的版本、用的哪套模型、接口地址，以及各块各自的数字。两份报告对着看，比的是机器和模型。
  6. 长度档是题的一部分，不是随手填的参数——分数按各档一起算，少跑一档分数就整体往下走。界面上只给看，不给改：让人看清这一轮要打哪几档，但没有任何改它的入口。超出这款模型窗口的档跳过并按零计入分数，那是这款模型的实情，不是题变了。
  7. 万一有人绕过界面用别的档位跑出一份报告，报告自己要说清「这份分数只能跟同样档位的报告比」，别让人截个图就当成横比结论。
  8. 表上写的字数必须就是真发出去的字数。太短的档凑不出来（底稿自带系统说明、用户话、指令和整份工具清单），这种档直接跳过，不许写一个做不到的字数充数。
- **关键取舍**：底层只负责按旗鱼的方式把请求发出去；题跟旗鱼版本脱钩。换过这套标准后题版本升一档，旧报告不能和新的比。宁可不给「只跑短档省时间」这个方便，也不要一屋子互相比不了的分数。
- **明确不做**：不评模型会不会干活、不打质量分、不跟公开榜单比、不自动扫全网模型。不把当时正在用的提示词或工具表现读进来当题。

### 一发的数不算数，每档打几发取中间那发

- **问题**：同一档连着跑两轮，首字延迟一次两秒、一次五秒都出现过。拿一发的数去比两台机器、两款模型，比的多半是当时网络的脾气，不是接口的本事。
- **成功标准**：
  1. 默认每档打三发，用户可以自己改（也可以只打一发赶时间）。这次打了几发要写进报告——两份报告对着看，先确认口径一样。
  2. 三发不是同一档连打，而是整套题跑完一遍再跑第二遍。三发落在不同时间段，才摊得掉网络和排队的偶然。第一遍跑完表就填满了，后面两遍逐步把数字校准。
  3. 表上显示的那一行，是按首字延迟排在中间的那一发的**整行数据**。不把各个数字分别取中位再拼成一行——那一行是谁也没跑出来过的。
  4. 任何一发失败（限流、断流、被截、该调工具没调），这一档就算没过，备注写明是第几发挂的。
  5. 各发之间同样不许吃上一发的缓存，每一发都当没跑过。
  6. 中途停掉时，已经打完的发照常留在表上，不因为后面没跑完就整档作废；报告里写的是实际打成了几发。
- **关键取舍**：宁可一轮跑得久一些，也不拿单发的数当结论。打的发数越多，一整轮里撞上偶发限流、断流的机会也越大，这是认了的——接口不稳本来就该在报告上看得见，赶时间或线路明显不稳时把发数调成 1。不报 95 分位、99 分位——三五发算这个没有统计意义，报出来只是把噪声打扮成精度。也不做预热请求：预热会破坏「每一发都冷启动」。
- **明确不做**：不按成功率给分数打折（失败就是没过）。不做变速率、泊松到达、上千并发那种基础设施级压力测试——那是专门工具的活。

### 主轴是上下文长短，写速记在每一档上

- **问题**：旗鱼一场活的上下文会自己涨。很多接口短对话还行，一长就变慢、限流、断流，或写到一半被截。旗鱼也经常让它写很长——上下文已经很长还在写，只回一个字看不出写速，只在最短档写一段也看不出后面几档会不会变慢。
- **成功标准**：
  1. 档位就是内置那几档（四千、一万六、三万二、六万四、十二万八字），界面上只给看不给改。不自动打到窗口边上——有的窗口上百万，那一档太大。
  2. 这款模型窗口装不下的档自动跳过，并说清为什么没打。窗口按对方报的 token 算，题按字数垫。
  3. 每一档只打一路，打完再打下档。跑的时候能停。
  4. 每一档看：成不成功、第一个字多久出来、整轮多久、写出多少、首字之后每秒多少字、有没有被限流、流式会不会断、输出有没有被截断。
  5. 每一档都写那段冻住的话，不是只回一个字。上下文变长以后稳不稳、写得快不快，都在这一档里看。
  6. 要它照抄的那段话和指令，放在最贴近它开口说话的地方，不能埋在垫料前头。埋了它就只在最短一档照抄，越长越自己发挥，各档写出的长短对不上，写速也就没法横着比。
  7. 每一档都要真把整份工具清单发出去。可以叮嘱它别调工具，但不能因为这句叮嘱让接口顺手把清单摘掉——主轴最该按真实请求的份量发。
  8. 它要是不听话真去调了工具，这一档算没过，备注写明调了哪个。
  9. 有的模型偶尔不照抄、自己发挥。写出来的不是那段话、或者照抄完又长出一大截时，这一档要在表上标出来。看的是它说出口的正文，不把思考过程算进去，否则会吐思考的模型整片被冤枉。标记只管给人看：不判失败（东西确实写出来了），分数也照常算——写速量的是每秒多少字，写长写短本身不抬高它。
  10. 不同长度之间不能吃上一档的缓存。短档填进去的字不能刚好是长档的开头，每一档都当没跑过。
- **关键取舍**：宁可每档都冷启动，也不为了省一点预填去复用提示缓存。写速不另开一块——旗鱼真实用法是上下文已经很长还在写，拆开就对不上。各档能横着比，靠的是每档都写出同样那段字，不是指望它自觉。
- **明确不做**：不把限流悄悄重试掉——限流、失败都记进报告，否则两边比不了。不靠接口的提示缓存来加速后几档。不自动换模型。不另打一档只测写速。不评写得好不好，不让它自由发挥成长短不一的文章。

### 真的在调工具

- **问题**：带着工具清单和真吐出一次工具调用不是一回事。有的接口清单吃得下，一吐调用就慢、截断或把流掐死。
- **成功标准**：
  1. 必须真的发出一次读文件那样的工具调用，不能用一段话代替。
  2. 不在本机真执行，回一段冻住的结果；再看它接到结果后能不能把这一轮收住。
  3. 收尾这一步同样把整份工具清单发出去。拿到结果还去叫下一个工具，就是没收住，算没过。
  4. 记下有没有吐出工具、会不会说到一半被截、两段各花多久、有没有被限流。
- **关键取舍**：只走这一次「发起调用 → 处理返回结果」的往返，证明接口吃得下旗鱼那种形状。不强迫接口「必须调工具」——有的模型一强迫就直接报错，旗鱼平时也不会这么发。题里写清楚要调；它不调，这项才算没过。这两步都走这款模型自己配的输出上限，压测不另卡一道更小的——否则思考先占满额度，会被当成说到一半。三路并发才故意只留一句的空。
- **明确不做**：不跑完整场秘书任务，不真改文件，不评它会不会干活。

### 同时打几路

- **问题**：桌上任务、联络、关切经常一起跑。单路没事，几路一起就限流、排队、互相拖。
- **成功标准**：
  1. 三路一起打同一道短题（四千字，只回一句）。
  2. 记下每一路成败、首字、整轮、有没有限流。
  3. 比的是三路一起上来时谁被排到后面，看最慢那一路第一个字多久出来，不看谁写得长。
  4. 一路要真回出话才算过：被截断、一个字没有、或者掉头去调工具，都算这一路没过，这一项随之为零。
- **关键取舍**：三路是默认，像桌面上常见的三件套；不做可调的扫表。题里叮嘱只回一句，但不另卡一道更小的输出上限——思考型模型会先把额度花在想上，一卡就被当成说到一半，平白判一路失败，总分跟着归零。
- **明确不做**：不做成网站压测那种一路加到打挂；不模拟三场内容不同的真任务。

### 一次跑完三块

- **问题**：拆开跑，两份报告对不齐，也容易只打自己顺手的那块。
- **成功标准**：点开始按顺序打完：上下文长短（含写速）→ 工具往返 → 三路并发。一张报告三块表。跑的时候能停。
- **关键取舍**：三块共用同一套冻住的题和同一套模型，才好比。
- **明确不做**：不做成互不相干的几套工具。

### 报告是给人对着看的表

- **问题**：比的是数，不是过/不过的打分。选型时几块表对着看又费劲。
- **成功标准**：
  1. 跑完就是三块表，数字能看懂。长度表上同时有首字和每秒多少字。
  2. 跑的时候一眼看得出打到哪一步、还剩多少；哪一档没过、为什么没过，扫一遍就知道，不用点开细看。
  3. 能把整份报告存下来或复制走，换一套模型再跑，两份对着看。
  4. 跑完有一个压测分，下面拆成四项：上下文、写速、工具、并发。写速从长度表各档来，不另打一次。同一套题、同一个版本下，分高就当更快更好。
  5. 长度这一项逐档累加：跳过的档、失败的档各自贡献零，能打到更长还稳的自然分高。工具往返和三路并发是整项判定——其中一步没收住、其中一路没过，这一项就是零。
  6. 一项是零，总分也是零。
  7. 四项的分要落在同一个量级上：一台正常机器跑下来，四项都该在同一个数量级里。任何一项都不该因为标尺没校准，一项就把总分带偏。
- **关键取舍**：跳过算零，能打到更长还稳、还写得动的才会分高。不为了好看把没打的档抹掉。一项判零必须是真出了问题，不能是压测自己卡出来的假失败——假失败会让一台好机器拿零分，比不准更糟。
- **明确不做**：不估费用（各家价目不同）；不把压测记进对话历史。不跟另一版题的分数比。不评模型聪不聪明。
- **已知偏差**：会把思考过程流式吐出来的模型，「第一个字」量到的是第一个思考的字，写出的字数也含思考。拿这类模型和不吐思考的模型对比时，首字和写速这两个数不是同一回事——要么只在同类之间比，要么看整轮。
